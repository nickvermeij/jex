# JEX back-end assessment

A versioned REST API for managing companies and vacancies, built with ASP.NET Core, EF Core and SQLite.

## Requirements

- .NET 10 SDK
- Node.js supported by Angular 22 (20.19+, 22.12+ or 24+) and npm 11 (for the optional Angular frontend)

## Run locally

Start the API in the first terminal:

```bash
dotnet restore
dotnet run --project src/Jex.Assessment.Api
```

In development the API applies migrations and seed data automatically. Swagger UI is available at `http://localhost:5023/swagger` for interactively testing the endpoints. The generated Swagger document is available at `/swagger/v1/swagger.json`; the built-in OpenAPI document remains available at `/openapi/v1.json`.

Start the Angular frontend in a second terminal:

```bash
cd src/Jex.Assessment.Web
npm install
npm start
```

Open `http://localhost:4200`. The Angular development server proxies `/api` requests to `http://localhost:5023`, so no development CORS configuration is required.

### Frontend capabilities

- Responsive vacancy overview built with Angular and Tailwind CSS
- Only companies with active vacancies are shown; each result contains only its active vacancies
- Nearby search using Rotterdam, Amsterdam or the browser's current location
- Configurable search radius from 10 to 100 kilometres
- Self-service vacancy submission, saved by the API as a draft
- Loading, empty, validation and API error states

## Development seed data

Debug seed data is enabled in `appsettings.Development.json`:

```json
{
  "SeedData": {
    "Enabled": true
  }
}
```

When the application starts in the `Development` environment, it first applies pending EF Core migrations and then runs `Infrastructure/DevelopmentDataSeeder.cs`. The seed is never executed in other environments.

The following scenarios are added:

| Company | Location | Vacancies |
|---|---|---|
| JEX | Rotterdam | One active vacancy and one draft |
| Canal Tech | Amsterdam | One active vacancy |
| Dom Digital | Utrecht | One closed vacancy |

All companies have structured addresses and coordinates, so the data can also be used to test the nearby-search endpoint. The mix of vacancy statuses makes it possible to verify that the vacancy overview only returns companies and vacancies that are active.

Start the API with:

```bash
dotnet run --project src/Jex.Assessment.Api
```

The seed is idempotent: companies and vacancies use deterministic GUIDs, and the seeder checks which records already exist. Restarting the application therefore does not create duplicates. If only part of the seed data exists, only the missing records are inserted.

Disable seeding temporarily without modifying a settings file. Development migrations are still applied:

```bash
dotnet run --project src/Jex.Assessment.Api -- --SeedData:Enabled=false
```

To start again with a completely clean debug database, stop the API, delete `src/Jex.Assessment.Api/jex-assessment.db`, and start the application again. The migration and seed will recreate the database.


## Assumptions and decisions

- Deleting a company cascades to all its vacancies at database level.
- The self-service `POST` endpoint requires only a title and always creates a `Draft`. The backoffice `POST` endpoint also requires a description and accepts a status. Vacancy statuses are serialized as `Draft`, `Active` or `Closed`.
- IDs are UUIDv7 GUIDs. They can be generated by the API without a database round trip and UUIDv7 has better index locality than random UUIDv4 values. IDs are identifiers, not security tokens.
- A vacancy has `Draft`, `Active` or `Closed` status.
- Backoffice vacancy creation requires both title and description.
- Self-service vacancy creation only requires a title, following user story 3. It creates a `Draft`; the backoffice must add its description before activating it.
- The vacancy overview endpoint returns only companies with at least one active vacancy and includes only active vacancies.
- Read-focused and backoffice route groups express different use cases, but are not security boundaries. Authentication and authorization are explicitly out of scope.
- DTOs form the API contract; EF Core entities are not exposed directly.
- An address is an EF Core owned value object with street, house number, postal code, city, ISO-like two-letter country code and optional coordinates. Latitude and longitude must be supplied together.
- Nearby search only returns companies with active vacancies. With SQLite, a latitude bound is applied in SQL and exact Haversine distance is calculated for the remaining candidates. At production scale this should use a spatial database/index such as PostGIS or SQL Server spatial.
- Coordinates are supplied by the caller; automatic geocoding is intentionally not coupled to company creation.
- SQLite keeps the assessment self-contained. A production database may require provider-specific configuration.

## Deliberately out of scope

- Authentication and authorization
- Automated API tests, as stated in the assignment; the Angular frontend does contain component and API-client tests
- Pagination and concurrency tokens; these would be next steps when data volume and concurrent editing requirements are known
